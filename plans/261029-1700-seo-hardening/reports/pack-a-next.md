## Addendum 3: hidden round-trip code (owner decision)
- Public `booking-config`: `has_code` (a legacy `code` is accepted and dropped at parse; promos with neither are ignored). The real code is read only server-side from the WP private route (`src/server/promo-secrets.ts`: `GET <WP>/wp-json/haivan-web/v1/promo-codes`, header `X-HV-Secret: $HV_WP_SHARED_SECRET`, body `{codes:{"<promoId>":"<code>"}}`, override URL with `HV_WP_PROMO_CODES_URL`; in-process cache 5 min, last-good; never passed to client components, not in Next's cache).
- Client token `@auto:<promoId>:<outboundOrder>` in `seat.promotion` / `codes[].promotion` / `seats[].code` (`lib/auto-promo-token.ts`); label from public config via the promo id. Auto-apply only on the return leg (`chang=ve` + `don_di`); combo auto-apply and badges disabled behind `AUTO_COMBO_ENABLED=false` (`lib/promo-flags.ts`).
- BFF (`/api/hv/gw`): `prepareAutoPromo` runs on POST promotion/check-promotions and POST bookings only (token elsewhere -> 422). Before substituting it checks, with the user's token: promo active/roundtrip; return trip leg (identified from ticket coordinates, <= 8 km of corridor end/stop points) = promo corridor + direction + travel window (dates, weekdays, hours, book-ahead, seats); outbound `don_di` (fetched via GET bookings/{don_di}?merchant_code=) exists for this customer, paid (`payment.type`), reverse leg of the same corridor, departs before the return trip, and return seats <= outbound live tickets. Otherwise 422 with a friendly message and nothing is sent upstream. Substitution is a byte-exact replace (query uses the same qs encoding, JSON uses JSON.stringify), so apigw sees the same bytes as a manually typed code. Responses of bookings*, promotion/*, admin/search-code-hide, price-ticket, v4/* have the real code masked back to `@auto:<promoId>`.
- Manual code entry unchanged (tested). Tests: `src/server/promo-hidden.test.ts` (15: substitution byte-equality, masking, rejections incl. unpaid/not-reverse/after/seats/direction/inactive/combo/travel window/missing don_di/other endpoint/multi-promo/secret route down), config tests (no `code` leaks), auto-promo tests rewritten for tokens, e2e: public config/HTML/JS never contain the code.
- Limits to know: corridor/direction of a trip is inferred from coordinates (fail-closed: unmatched = no discount); one-time use per outbound order is not tracked on our side (ERP promotion quantities must enforce it); first masking after a cold start can miss until the code map is warmed (it is warmed by any promotion/bookings call and by token requests).
